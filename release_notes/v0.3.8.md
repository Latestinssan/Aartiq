# 🚀 Aartiq Browser v0.3.8

**Channel:** Pre-release. Published as `v0.3.8-beta.1`; `v0.3.7` remains the
current stable release until this is promoted. Firebase download links were not
repointed by the beta.

## Local listener authentication and shell approval defaults

Two defaults changed. Both were unconditional before.

---

## Local listeners now require a credential

The MCP browser bridge listened on every network interface, answered every route
without a credential, and sent `Access-Control-Allow-Origin: '*'`. Pairing was
confirmed the moment any client opened the SSE stream, so the pairing token was
recorded state rather than a boundary, and a client that could reach the port
could also choose the token it would later be compared against.

Every listener now runs the same gate on every request, including SSE and every
POST route:

- **Bind.** The MCP browser bridge binds `127.0.0.1`. Exposing it on a LAN or
  Tailscale is a setting, off by default, and requires the token like every other
  mode. The setting must be a real boolean — a hand-edited config containing
  `"remote": "false"` does not open the listener.
- **Token.** A per-process token is required. It is generated by the server rather
  than supplied by a caller, and the route that previously accepted a
  caller-chosen token is gone.
- **Host.** The `Host` header must be the loopback host and that listener's own
  port. A request that names a hostname which resolves to loopback is refused.
- **Origin.** A request carrying a browser `Origin` must be on an allow-list of
  the app's own origins. Requests with no `Origin` are not browser requests and
  are authenticated by the token instead.
- **Logging.** Rejections record the reason, method and path. No token value is
  written to a log.

Also applied to the Agent API HTTP server, which had the same absence of checks
and auto-registers any unknown agent id, and to the native macOS bridge, whose
CLI token already existed and was written to `~/.aartiq-token` with mode `0600`
but which no route read.

`x-agent-id` remains an identifier. Authentication is the token.

The token is accepted as `Authorization: Bearer`, `X-Aartiq-Token`,
`X-Aartiq-Native-Token`, or a `?token=` query parameter. The third of those is the
header the shipped CLI and the macOS native panels send, and it is worth naming
because its absence broke them: the first cut of this gate did not read it, so
every native-bridge request was answered with 401. The header list is now pinned
by a test that reads the shipped clients rather than a copy of their header, so a
client that changes what it sends fails the suite instead of the app.

### What users will notice

The Claude Desktop config Aartiq writes now carries the session token in the
`mcp-remote` URL, because `mcp-remote` accepts a bare URL and nothing else. The
token is regenerated on every Aartiq start, so **a config written before an
upgrade, or before the last restart, will be answered with 401** until
Auto-Configure is run again. The setup screens say so and show the current URL.

## Shell commands no longer auto-run

On every start, Aartiq created session grants for low and medium shell commands
with an eight-hour lifetime. No setting controlled it. The classifier treated
every non-destructive command as medium, so the grant covered `cp`, `mv`,
`mkdir`, `npm`, `git`, `curl` and `osascript`: those ran with no prompt for eight
hours after each launch.

- Those grants are no longer created.
- Auto-approval is now the `autoApproveLowRiskShell` setting, **default off**. It
  covers read-only commands only.
- Medium-risk commands prompt every time.
- The `autoApproveMidRisk` setting no longer applies to shell commands. It still
  applies to MCP tool actions, which is a separate question.

### The classifier now has a `low` tier

It previously returned `high` for a destructive pattern and `medium` for
everything else, so `low` was never produced for a shell command. The per-command
table now lives in one file that both the classifier and the documentation
generator read, so the two cannot describe different systems.

`curl`, `wget`, `npm`, `npx`, `git`, `node`, `python`, `osascript` and the other
network- or script-capable commands are not `low`. An unrecognised command is
`medium`, never `low`. A command line containing a URL is never `low`.
`chmod` stays `high`.

### "Allow Always" now applies to one command

Grants were keyed on the first word, so answering "Always" to one `curl`
authorised every later `curl` regardless of its arguments. Grants are now keyed
on the whole command line.

Permanent grants are no longer offered for network-capable, script-capable and
destructive commands, or for anything with a URL in its arguments. **Allow Once**
is always available. `cp`, `mv`, `mkdir` and `touch` can still take a grant, and
that grant now matches that exact command line only.

Eligibility is an allow-list rather than a deny-list. A permanent grant requires a
binary that appears in the classifier's table, so a binary it has never
classified is offered Allow Once only. That command is classified `medium`
precisely because nothing is known about it, and a grant which promises to repeat
something nobody can describe is a promise about behaviour rather than about the
text. Nothing becomes unusable: Allow Once still works, and for an unclassified
binary it is now the strongest answer available.

Being in the table is a weaker signal than being known safe, and deliberately so.
`medium` local writes keep their grants because the effect of repeating them is
visible in the dialog text, unlike a network fetch or a script.

Grants you made before are migrated on first load:

- a grant for a command that can still take one is kept, and now covers only the
  exact command line rather than every invocation of the binary;
- a grant for a network-capable, script-capable or destructive command is
  **dropped**, and each drop is written to the audit log. These were the entries
  carrying the most authority for the least visibility. Re-approve them
  individually if you want them back;
- a grant for a command the classifier does not recognise is **dropped** on the
  same terms, for the same reason.

Grants you made deliberately in **Settings → Permissions** are untouched.

- `tests/local-server-auth.test.js` — 44 cases over real sockets: all-interfaces
  bind refused by default, 401 without a token, 403 on a foreign `Host`, 403 on a
  foreign `Origin`, 200 for valid loopback plus token, and the pairing flow end

## The documentation is generated from the code

The tier table, the test counts and the live repository figures on the project
site are now written by scripts that read the same files the runtime reads, and
`npm run docs:check` fails if a published number or claim disagrees with the code
or with the site's single source of truth. It also rejects a page that describes a
security default the code no longer has — which is how the site was found to be
still advertising a startup session grant after that grant had been removed.

Worth being precise about the limit: the gate runs from `npm run docs:check` and
in no GitHub workflow yet, so it protects a commit only if someone runs it.

## Android signing key and Firebase config were in a public repository

The release upload keystore was committed in plaintext at
`flutter_browser_app/android/app/keystore-base64.txt`. Because this repository is
public, that key has been extractable by anyone since it was created:

```
git show <commit>:flutter_browser_app/android/app/keystore-base64.txt | base64 -d > key.jks
```

**The key has been rotated.** `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_PASSWORD` and `ANDROID_KEY_ALIAS` now hold a new key, and
`GOOGLE_SERVICES_JSON` was updated to match.

Rotation is what closed the hole. Untracking the file does not, and neither would
rewriting history, because anyone who cloned before this release already holds the
old key. A history purge was deliberately left out of scope.

Two ignore rules were also wrong, which is why the file stayed tracked after an
earlier commit claimed to have gitignored Firebase config:

- `.gitignore` ignored `flutter_browser_app/ios/Runner/GoogleService-Info.plist`,
  but the file lives at `flutter_browser_app/ios/GoogleService-Info.plist`. The
  rule matched nothing.
- Nothing covered `keystore-base64.txt`. The existing patterns matched `*.jks` and
  `*.keystore`, and this file is a `.txt`.

Both files remain on disk locally; only tracking was removed. CI still generates
them from secrets.

### Android users may have to uninstall before updating

**This could not be verified from the repository.** If release APKs were signed
directly with the upload key and Play App Signing was never enrolled, Android
cannot update an existing install across a key change, and users would have to
uninstall before installing this version. If Play App Signing is enrolled, the
rotated key is only the upload key and existing installs update normally.

Nothing in the repository settles which of those is true. Check the Play Console
before telling anyone the Android upgrade is seamless.

### Flutter version numbers had stopped moving

One tag covers both the desktop app and the Flutter companion, but each had its
own version file, so `pubspec.yaml` had silently drifted to `0.3.5+10` against a
`package.json` at `0.3.7`. No workflow passed `--build-number`, so Flutter fell
back to `+10` on every run and `versionCode` stayed pinned at **10** across v0.3.5
to v0.3.7 — which is what turned each Play upload into a fresh version-code
conflict.

`sync-version.ts` now rewrites pubspec's `version:` line from `package.json` and
derives the build number from semver, so it climbs on its own. `auto-tag.yml` fails
the release if the two versions disagree.

## iOS could not initialise Firebase at all

`GoogleService-Info.plist` existed at `ios/GoogleService-Info.plist` but was never
referenced by `Runner.xcodeproj`, so it was never copied into `Runner.app`.
`Info.plist` carries no inline Firebase keys and `AppDelegate.swift` initialises
nothing, so `Firebase.initializeApp()` had nothing to configure from and **iOS
sign-in could not work**. Separately, `PRODUCT_BUNDLE_IDENTIFIER` was
`com.aartiq-com.aartiq` while the plist declares `BUNDLE_ID = com.aartiq`, which
Firebase treats as fatal.

- The plist is now wired into the Runner target. It resolves to `ios/Runner/` —
  which is exactly where all five CI workflows already wrote it from the
  `GOOGLE_SERVICE_INFO_PLIST` secret, so no workflow change was needed.
- `PRODUCT_BUNDLE_IDENTIFIER` is aligned to `com.aartiq` across Debug, Release and
  Profile, matching both the plist and Android's `applicationId`.
- The deployment target is raised to 15.0 in the Podfile and the Xcode project,
  with a `post_install` hook forcing every pod target to match. Xcode 27 refuses to
  build any target below 15.0 and the pods still declared 9.0 to 13.0, so the build
  failed before compiling a file. **This drops iOS 13 and 14 support**, which
  Xcode 27 requires and which nothing relied on.

Verified: `flutter build ios --no-codesign --debug` succeeds, the built `Runner.app`
contains the plist, its `BUNDLE_ID` matches the app's `CFBundleIdentifier`, all 14
plist keys are identical between source and bundle, and its `CLIENT_ID` matches
`_iosClientId` in `lib/auth_service.dart`.

## The desktop app could not start on Linux

`setupLinuxIPCHandlers()` registered five `linux:` IPC channels, and `main.js` —
having called that function inside its `platform === 'linux'` guard — then
registered the same five names at module scope. Electron's `ipcMain.handle` throws
on a second registration of a channel, the call was not wrapped in a `try`, and it
ran at module top level. **On Linux the main process stopped executing at
`linux:notify`, before the window was created**, and the four registrations after it
never happened either.

macOS and Windows were unaffected, which is why it went unnoticed for so long.

`main.js`'s copies are the ones kept rather than the module's, and that choice is
load-bearing. They carry a `process.platform !== 'linux'` check that answers
`{ error: 'Not Linux' }` on the other two platforms, where
`setupLinuxIPCHandlers()` never runs at all. Removing those instead would have
removed the crash *and* left every `preload` invoke for those five channels
rejecting with `No handler registered` — trading a Linux-only crash for silent
breakage on two platforms.

This fix is also what made the defect testable. `linux-integration.js` named a
parameter `interface`, which is a reserved word in strict mode and therefore in
every Jest module, so the file could not be loaded by the test runner at all and no
test had ever been able to call `setupLinuxIPCHandlers()` and reach the crash.
`tests/linux-ipc-registration.test.js` now calls the real function against an
Electron stub whose `ipcMain.handle` throws on a duplicate, exactly as the real one
does.

**Nobody booted the AppImage to confirm this.** The fix is backed by that test and
by reading the two registration sites; the artifact itself was not run on Linux.

### Five channels are still registered, and still dead

`linux:get-desktop`, `linux:shortcut-action`, `linux:speak`, `linux:get-voices` and
`linux:start-voice` are each registered once and invoked by nothing in the
repository. Fixing the crash removed the duplication, not the dead channels, and
the docs page and its gate both still report them.

## An approval ticket could be redeemed twice

`consumeTicket` in `src/lib/approval-gate.js` is async, and its only `await` sat
between the check that a ticket was unconsumed and the mark that consumed it. Every
simultaneous redemption passed the check, then all reported success — eight
simultaneous redemptions of a single ticket returned eight successes.

The claim now happens above the first `await`. JavaScript runs synchronous
statements without interleaving another async caller, so deleting the ticket there
is the atomic claim, and a concurrent caller now finds nothing to redeem. The hash
check still runs afterwards, and a mismatch still fails closed leaving nothing
redeemable.

**This module has no callers.** It is not wired into the app and is not a
documented feature, so no user was affected and this is not a live vulnerability.
The approval path the app actually uses is `src/core/approval-ticket-manager.js`,
whose `redeemTicket` is fully synchronous and therefore has no interleaving point.
Two tests now assert that eight simultaneous redemptions of one approved ticket
yield exactly one success, so an `await` cannot be introduced there without the
suite noticing.

One deliberate behaviour change: a concurrent `peekTicket` now reports
`APPROVAL_INVALID` during the consume window where it previously reported `valid`.
The ticket is claimed at that point, so `invalid` is the honest answer.

### A second defect here, reported and not fixed

Ticket ids are `ticket-${perInstanceCounter}-${Date.now()}`, where the counter is
per instance, while the ticket store is module-level. Two `ApprovalGate` instances
built in the same millisecond therefore mint identical ids, and the first
redemption invalidates the second unrelated ticket. The id scheme is unchanged,
because changing it is a behavioural change to a module with no callers and not one
to smuggle into a security fix.

## The feature documentation is now checked against the code

The published feature pages had drifted from the source. Eight claims on the Cloud
Sync page described behaviour the sync service does not have: a three-tier
Read Only / Standard / Trusted permission ladder, mDNS discovery, a 60-second
pairing timeout, transfer and per-item size ceilings, an audit trail, automatic
conflict resolution, and an encryption guarantee attributed to a `shared-keychain.js`
file that does not exist.

All eight are corrected. The claims that are true are kept and made more precise —
end-to-end encryption does apply to the cloud path, and the page now says plainly
that the local WebSocket is not covered by it.

The correction is enforced rather than trusted.
`tests/docs-sync-match-source.test.js` holds 17 assertions reading both the rendered
page and `src/lib/WiFiSyncService.ts`, stripping comments before matching so that
documenting a removed claim does not trip the gate. Before the fix, **12 of its 15
assertions failed**; the 3 that passed were the true encryption claims. Three
separate mutations of the corrected page are each caught — re-adding the 60-second
hero tile, the mDNS line, or widening the encryption claim.

`npm run docs:check` fails when a published number or a security claim disagrees
with the code or with the site's single source of truth, and the manifest records
which test or manual check each feature rests on.

### Still unverified, and still published as unproven

Four features are marked `works` with neither a test nor a signed-off manual check,
so no page may present them as available: `apple-intelligence.generate-image`,
`apple-intelligence.summary`, `http-api.native-bridge` and
`keyboard.global-hotkeys`. One manual check, `siri.appintents`, is unsigned.
Eighteen further rows are awaiting a maintainer decision and have neither been
implemented nor removed.

Written up as issue drafts in `aartiq-browser/docs-audit/issues/`:

- `allow-always-granularity.md` — argument-aware policy for permanent grants
- `remote-mode-auth-design.md` — how LAN/Tailscale mode should authenticate
- `wifi-sync-bind-address.md` — WiFi sync binds all interfaces by omission
- `pdf-sync-bind-address.md` — background service serves on `0.0.0.0`
- `pairing-token-in-url.md` — the token has to travel in the `mcp-remote` URL

Found while writing this release, and still open:

- **Play App Signing enrolment is unknown**, so whether Android users must
  uninstall before taking this release cannot be answered from the repository. This
  is the one item here that may need an action before the release goes out.
- The Android keystore remains retrievable from git **history**. Rotation closed the
  hole; a purge would not help anyone who already cloned, so it was left alone.
- Five `linux:` IPC channels are registered once and invoked by nothing.
- Approval ticket ids can collide between two `ApprovalGate` instances built in the
  same millisecond.
- `security.monitoringOnlyChannels` carries a standing `TODO(verify)` warning: the
  22-of-9 IPC figures it cites are not present in the action inventory. Nothing
  renders them.
- `docs:check` still runs only when a person runs it. It is not in any GitHub
  workflow, so it protects a commit only by being remembered.
