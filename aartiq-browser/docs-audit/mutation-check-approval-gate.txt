Note on the surviving mutation
-------------------------------
`consumedTickets.add(ticketId)` survived: no current assertion fails without
it. The mark is defence-in-depth against an id being re-minted after it was
consumed — createTicket would put the id back into `tickets`, and the
consumed-mark is what rejects it. With the singleton gate the application
uses (globalApprovalGate), the counter never restarts, so a re-mint cannot
happen today; it becomes reachable again the moment a second ApprovalGate
instance exists (the scenario that produced the observed flake in this very
test file). Reported as a coverage gap: either a test that forces the
re-mint, or a per-process random component in the id scheme, is the
maintainer's call. Not papered over here.
